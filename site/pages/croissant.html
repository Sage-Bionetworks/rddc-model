RDDC and Croissant

An RDDC sidecar follows Croissant 1.1. Croissant tools can read its files and file sets. RDDC tools also read the clinical fields. This page explains what the formats share and what RDDC adds.

Overview slides: the standards rationale, the four Croissant layers, RDDC needs and a side-by-side comparison.

Foundations introduces the format. Croissant describes a dataset's files (cr:FileObject, cr:FileSet) and the tables in them (cr:RecordSet, cr:Field) on top of schema.org's Dataset.

The design in one paragraph

Every file uses "@type": "cr:FileObject", and every file set uses "@type": "cr:FileSet". The RDDC class goes in additionalType and determines the extra required fields. The sidecar keeps existing Croissant and schema.org property names. RDDC fields use camelCase in the rddc: namespace. The embedded context combines Croissant's context with RDDC terms; the builder rejects any attempt to redefine a Croissant term.

One file, two ways

The same compressed FHIR NDJSON file, described in plain Croissant and in an RDDC sidecar:

Plain Croissant

{ "@type": "cr:FileObject", "@id": "observations", "name": "Observation.ndjson.gz", "contentUrl": "https://example.org/fhir/Observation.ndjson.gz", "encodingFormat": "application/gzip", "sha256": "e047db5f…" }

RDDC sidecar

What changed, reading top to bottom:

  • @id is a UUID URN that identifies this file across every batch of the source, not a local label.
  • additionalType names the RDDC class. Because it is rddc:FhirNdjsonFile, resourceType is required and encodingFormat must be application/fhir+ndjson.
  • contentUrl is relative to the batch prefix, so the sidecar stays valid wherever the batch is stored.
  • contentSize and sha256 are required, so receipt can verify the upload.
  • encodingFormat describes the content after decompression; compression says how it is wrapped.
  • modality, recordCount and the per-file sensitivity override are RDDC additions for routing and de-identification.

One collection, two ways

Plain Croissant

{ "@type": "cr:FileSet", "@id": "fhir-files", "name": "FHIR export", "encodingFormat": "application/fhir+ndjson", "includes": ["fhir/*.ndjson"] }

RDDC sidecar

The RDDC version keeps the Croissant glob in includes, so generic loaders still find the files, and adds:

  • hasPart, listing members explicitly by @id;
  • conformsTo, pinning the standard and version (FHIR R4 with US Core 6.1), which picks the processing lane;
  • class-specific facts such as exportTime and subjectCount.

How generic Croissant tools see a sidecar

A Croissant tool reads the standard files, file sets, checksums and media types. It ignores RDDC terms such as modality and subjects. Run make check with mlcroissant installed to check that every example loads.

import mlcroissant as mlc ds = mlc.Dataset(jsonld="examples/deposit_fhir_omop.json") for item in ds.metadata.distribution: # FileObjects and FileSets print(type(item).__name__, item.name)
Expect warnings, not errors

Croissant validators may warn about properties Croissant recommends but the sidecar leaves out on purpose, such as license. Those warnings are expected.

Why not plain Croissant, or a custom format?

  • Plain Croissant has no place for subjects, withdrawals, clinical standards or de-identification facts, and its open-world rules can't guarantee that a pipeline finds the fields it needs.
  • A custom format would need a separate mapping to work with Croissant tools and datasets.
  • Croissant plus RDDC terms works with Croissant tools while adding validation rules for clinical intake. An earlier draft of the model (0.2.0, snake_case groups and links) took the custom route; the model restarted at 0.1.0 when it moved to Croissant.
