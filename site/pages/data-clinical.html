Clinical data

Electronic health record extracts in FHIR, OMOP CDM and C-CDA, other clinical tables such as registries and patient-reported outcomes, consent tables, and clinical documents.

Data in a clinical standard

FHIR, OMOP CDM and C-CDA files always belong to a file set of their standard: FhirBulkExport or FhirBundleCollection, OmopCdmInstance, or CcdaDocumentSet. The file set's conformsTo gives the standard and its version, such as FHIR R4 with US Core 6.1 or OMOP CDM 5.4, from the pinned list. The files themselves do not repeat it.

FHIR

A FHIR file is one of three shapes. A Bulk Data export is NDJSON with one resource type per file, a FhirNdjsonFile. A Bundle, such as one patient's record from Synthea, is a FhirBundleFile; it lists its subjects, since a Bundle usually holds one person. A single resource that is not a Bundle is a FhirResourceFile. The resource type must be a resource type of the FHIR version the file set declares.

Device data already in FHIR form, such as Observations from a wearable, stays a FHIR file. Its file set declares the HL7 Personal Health Device IG alongside FHIR.

OMOP CDM

Each OMOP table is its own OmopTableFile, naming the table in cdmTable and the CDM version in omopCdmVersion. The table must exist in that version. OMOP foreign keys are defined by the CDM, so the sidecar does not describe them.

C-CDA

Each C-CDA document is a CcdaDocumentFile listing its subject. The document header carries its template IDs, and the file set gives the C-CDA release.

Other clinical tables

Registry, patient-reported outcome, claims and mortality tables that are not in a clinical standard are TabularFiles. The file's name and path identify the table. To describe its columns, or a join to another table, add a record set to the sidecar, and a data dictionary as a DocumentationFile.

Consent

A ConsentFile holds consent elements: which uses each listed subject agreed to. The platform applies them to access decisions rather than processing them as clinical data. A consent batch (interaction: consent) may include consent files; see the consent recipe.

Clinical documents

Notes, reports and scanned documents are ClinicalDocumentFiles. They are unstructured, so they are de-identified with a text scan, or OCR for scans, before use. Each lists its subject. Set containsFreeText (it is assumed true when unset). A scanned report can carry a processing hint for the OCR step; hints are informational only.

Sensitivity

  • Clinical data usually contains dates more precise than a year and may contain postal codes. Both are accepted at deposit and masked at release. Declare them with containsDates and containsZipCodes, or set them to false when the data has none.
  • Free text, in notes or in free-text fields of a structured table, needs a de-identification scan. Declare it with containsFreeText, on the batch or on the files that have it.
  • Direct identifiers such as names and medical record numbers must be removed before upload, which the batch confirms with directIdentifiersRemoved.

See the sensitivity flags for what each covers.
