Clinical data

Electronic health record extracts in FHIR, OMOP CDM and C-CDA, other clinical tables such as registries and patient-reported outcomes, consent tables, and clinical documents.

Clinical data standards

FHIR, OMOP CDM and C-CDA files are always delivered as a collection of their class's file set class: a FHIR export, Bundle collection or resource collection, an OMOP CDM instance, or a set of C-CDA documents. The collection declares the standard and its version, such as FHIR R4 with US Core 6.1 or OMOP CDM 5.4, so the files do not repeat it. The validator checks that every such file belongs to a collection of the right class.

FHIR

FHIR files have three forms. A Bulk Data export is NDJSON with one resource type per file, a FhirNdjsonFile in a FhirBulkExport. A Bundle, such as one patient's record from Synthea, is a FhirBundleFile in a FhirBundleCollection; it lists its subjects, since a Bundle usually holds one person. A single resource that is not a Bundle is a FhirResourceFile in a FhirResourceCollection. The resource type must exist in the FHIR version of the collection.

Device data already in FHIR form, such as Observations from a wearable, stays a FHIR file. Its collection declares the HL7 Personal Health Device IG alongside FHIR. FHIR files can embed documents and images, in DocumentReference, Media and Binary resources, whose content the class and the sensitivity flags do not describe; the same holds for C-CDA documents.

OMOP CDM

Each OMOP table uses an OmopTableFile with cdmTable, in an OmopCdmInstance whose conformsTo gives the CDM version. The table must exist in that version. The CDM already defines OMOP foreign keys, and CDM tables have no column for an image or recording, so a table contains no biometric identifiers unless it says so.

C-CDA

Each C-CDA document is a CcdaDocumentFile listing its subject. The document header carries its template IDs, and the document set gives the C-CDA release.

Other clinical tables

Registry, patient-reported outcome, claims and mortality tables that are not in a clinical standard are TabularFiles. The file's name and path identify the table. A data dictionary describing its columns is a DocumentationFile.

Consent

A ConsentFile records permitted data uses for each listed subject. The platform applies them to access decisions rather than processing them as clinical data. A consent elements table holds coded uses and dates, so postal codes, free text and biometric identifiers are false unless the file or batch says otherwise.

Intake forms

Responses to a patient intake form, exported as a table from REDCap or a clinic portal, are an IntakeFormFile. Its columns are the form's questions and its values coded answers, so it is read with the form's definition, named in formDefinition: a DocumentationFile in the same deposit, such as a REDCap data dictionary, or the URL of a published definition. Free-text answers make the file contain free text.

Genetic test results

Structured results of clinical genetic tests or molecular pathology, one record per test with its findings, are a GeneticTestResultFile. The laboratory's interpretation makes the file contain free text. Its signed report documents are ClinicalDocumentFiles that reportDocuments points to; sequencing data and variant calls go in the genomics classes. A report lists few variants, not a genome, so the class is not identifying.

Differential diagnoses

Candidate diagnoses ranked by a diagnosis support tool, such as a facial phenotyping or phenotype-matching tool, are a DifferentialDiagnosisFile: for each subject the top candidates with their rank, score and code. They are suggestions, kept apart from confirmed conditions. software and softwareVersion name the tool, diagnosisCodeSystems the code systems used, and wasDerivedFrom the files the tool analysed. A tool's export is structured; a PDF report is unstructured.

Clinical documents

Notes, reports and scanned documents are ClinicalDocumentFiles. They are unstructured, so they are de-identified with a text scan, or OCR for scans, before use. Each lists its subject. The whole document is free text, so every file counts as containing free text and cannot set containsFreeText; the other flags can still be set per file. A scanned report can carry a processing hint for the OCR step; hints are informational only. When the source records the kind of document, documentType names it with a LOINC Document Ontology value, such as referral_note; text processing and the OMOP note class depend on it.

Sensitivity

Clinical classes, including FHIR, are not automatically classified as identifying. Their files may still contain identifying information and require de-identification checks.

  • Clinical data usually contains dates more precise than a year and may contain postal codes. Both are accepted at deposit and masked at release. Declare them with containsDates and containsZipCodes, or set them to false when the data has none.
  • Free text, in notes or in free-text fields of a structured table, needs a de-identification scan. Declare it with containsFreeText on the files that have it.
  • Direct identifiers such as names and medical record numbers must be removed before upload.
