Core concepts

How a metadata sidecar identifies batches, files and subjects, and records sensitivity information.

Contributors, sources and batches

The RDDC Infrastructure Plan uses three terms:

Contributor
An organization that sends data. It has one S3 bucket and one or more sources. Identified by contributorId.
Source
One of a contributor's data sets, with one set of use terms, registered with the RDDC before the first deposit. Identified by sourceId.
Batch
One delivery of files for one source. One batch, one S3 prefix, one sidecar. Identified by batchId, which the contributor chooses and which is unique within the source.
s3://rddc-deposit-ta2/ bucket of contributor ta2-site-a └── src-ta2-01/ source ├── 2026-10-b01/ batch prefix → "url" in the sidecar │ ├── fhir/Patient.ndjson data files → "contentUrl": "fhir/Patient.ndjson" │ ├── fhir/Observation.ndjson.gz │ ├── omop/person.csv │ ├── registry/patients.csv │ └── _sidecar.json uploaded last; not listed in itself └── 2026-11-w01/ a later batch: a withdrawal └── _sidecar.json

The sidecar's url is the batch prefix, ending with a slash. Every contentUrl is relative to it. The sidecar describes every data object under the prefix and nothing outside it; it does not list itself.

Files

Every entry in distribution with "@type": "cr:FileObject" is one data file of the batch. How a file is described does not depend on the sidecar around it, so it has its own section:

  • How data is classified: the data class in additionalType, and the modality, structure and sensitivity facts it carries.
  • Describing a data file: file identity, media type and compression, measurementTechnique and the other class fields.
  • The family pages, from Clinical data to Documentation and other files, with a valid example of every class.

The rest of this page covers what the sidecar adds around its files: file sets, the subject table, sensitivity defaults, provenance and references.

File identity

In a sidecar, every file also has "@type": "cr:FileObject" and an @id, a UUID URN such as urn:uuid:0000000a-0000-4000-8000-00000000000a. The @id identifies one file of the source, not one upload:

  • It stays the same when the platform moves or re-registers the object.
  • Changed content is a new file with a new @id.
  • Identical content under two paths is two files with two @ids.
  • It is unique within the sidecar and never reused for a different file.

Use a lowercase UUID. The RDDC tool creates UUIDv5 values from the source, batch, path and checksum. It can reuse IDs from a previous sidecar for unchanged files. Other tools may generate IDs differently.

File sets

Files that form one collection, such as an OMOP instance or a FHIR bulk export, are grouped in a file set with "@type": "cr:FileSet" and an RDDC class in additionalType. A file set:

  • has a short local @id such as omop, not a UUID;
  • lists its members in hasPart, selects them with includes globs, or both. Every member must also appear in distribution. A glob is still needed alongside hasPart for generic Croissant loaders, which only read includes;
  • declares the standard it follows in conformsTo, which is required for FHIR, OMOP and C-CDA sets;
  • may give the period its data covers in temporalCoverage, schema.org's ISO 8601 interval such as 2019/2024. The sidecar document can give one for the whole batch. Use year or month precision unless the batch declares containsDates.

Subjects

The subject table lists every person in the batch, by the contributor's coded ID. It is how the RDDC checks a deposit against its participants table, and how a later withdrawal finds the right data.

A subject's identity is the combination of three values, which must be unique within the table and mean the same person in every batch of the source:

  • subjectId: the coded ID. Never a name, MRN or other direct identifier.
  • idSystem: where the ID comes from, such as fhir_patient_id (FHIR Patient.id) or omop_person_source_value.
  • identifierSystemUri: required when idSystem is fhir_patient_identifier, naming the identifier system.

Per-file subjects

A file may list the subjects it contains in subjectIds; each must match a row of the subject table. The list is required for formats that hold one person per file: FhirBundleFile, CcdaDocumentFile and ClinicalDocumentFile. It is optional for multi-subject tables and NDJSON.

Sensitivity

The sensitivity block describes data that de-identification and routing need to check. Use terms, access tier and date policy come from the source register and cannot be set in a sidecar.

Provenance

Use wasDerivedFrom to link a file to its input files in the same batch, or a file set to its input file sets. For example, an OMOP snapshot can point to the FHIR export it was built from. Synapse records the provenance of RDDC pipeline outputs.

Value origins

valueOrigins records how a tool filled in a value: its JSON pointer, origin (declared, detected or inferred), method and confidence. A person must confirm inferred values with "confirmed": true before validation passes.

Record sets

Record sets describe table columns. Use them for data dictionaries and joins between tables whose structure is not defined by a standard, such as visits.patient_id referencing patients.id. OMOP foreign keys and FHIR references are already defined by their standards.

Extensions and hints

The schema rejects unknown properties. Project details have two supported locations:

  • Extensions (additionalProperty, on the sidecar or any file or file set) hold project-specific values. Keys have the form ext:<namespace>:<key>. Tools that rewrite sidecars preserve them.
  • Processing hints (processingHints, on data files) are informational notes for a pipeline, keyed <namespace>:<key>. Any value used for a pipeline decision must be a defined schema field.
