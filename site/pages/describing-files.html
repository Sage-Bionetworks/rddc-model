Data file descriptions

Shared and class-specific fields, including media type, compression and assay.

Data file fields

Every data file needs additionalType (its class), name, contentUrl, contentSize, encodingFormat and sha256. Each family page lists its class-specific required fields. Shared fields:

contentUrl is the file's path within the upload, with no leading slash, no empty segments and no ... name is, by convention, the same path. sha256 verifies file integrity after upload.

Media type and compression

encodingFormat is the IANA media type of the content after decompression. Specify file compression in compression. A gzipped NDJSON file is encodingFormat: application/fhir+ndjson with compression: gzip, never application/gzip.

Each class lists the media types it accepts. Some formats have no registered media type. For those the schema uses a fixed convention rather than an invented x- type, and the class names the format:

  • Genomics formats each have a class (FastqFile, BamFile, CramFile, VcfFile, BcfFile) and use text/plain for text and application/octet-stream for binary. BAM, CRAM and BCF compress internally, so they leave compression unset; a .fastq.gz or .vcf.gz sets it to bgzf when written by bgzip, which an index requires, and gzip otherwise. Indexes are always binary.
  • Sensor signal formats each have a class (EdfSignalFile, WfdbSignalFile, DicomWaveformFile, VendorSignalFile); EDF and vendor formats are application/octet-stream, as are whole-slide and NIfTI images (ImageFile) and PLY 3D models.
  • JSON Lines is application/jsonlines, and Parquet is application/vnd.apache.parquet.

Measurement technique

Genomics, imaging and sensor files require schema.org's measurementTechnique to identify the assay or technique used for analysis. Each family has its own list of values, and each value maps to a term in an ontology such as OBI, NCIT or SNOMED CT (see Standards and mappings). Sensor files give a list, since one recording can combine several techniques.

Class-specific fields

These fields apply only to data files. Each family page lists the applicable and required fields.

Subjects, sensitivity and provenance

  • subjectIds lists the people whose data the file contains, by the contributor's coded IDs, never names or record numbers. It is required for classes that hold one person per file, such as FHIR Bundles, C-CDA documents, clinical documents and facial images, and optional for tables of many people.
  • sensitivity identifies content requiring de-identification checks: dates, postal codes, free text and biometric identifiers. A flag left unset takes the deposit's value (part 2), else the class default, else it is unknown and assumed true. A file cannot set a flag its class fixes: a genomics file holds none of them, a clinical document always has free text, and a facial image always has biometric identifiers. See the flags by class and the flag definitions.
  • wasDerivedFrom references the file's inputs, such as the alignment used to call variants.
