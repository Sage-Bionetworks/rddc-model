Describing a data file

The fields every data file carries, how to give its media type and compression, and the class-specific fields such as the assay that produced it.

Fields every data file has

Every data file needs @id, @type, additionalType, name, contentUrl, contentSize, encodingFormat and sha256. The class adds its own required fields, listed on each family page. These are the fields of DataFile, which every class inherits:

File identity

Every file's @id is a UUID URN such as urn:uuid:0000000a-0000-4000-8000-00000000000a. It identifies one file of the source, not one upload:

  • It stays the same when the platform moves or re-registers the object.
  • Changed content is a new file with a new @id.
  • Identical content under two paths is two files with two @ids.
  • It is unique within the sidecar and never reused for a different file.

Use a lowercase UUID. The RDDC tool creates UUIDv5 values from the source, batch, path and checksum. It can reuse IDs from a previous sidecar for unchanged files. Other tools may generate IDs differently.

contentUrl is the file's path relative to the batch prefix, with no leading slash, no empty segments and no ... name is, by convention, the same path.

Media type and compression

encodingFormat is the IANA media type of the content after decompression. If the bytes are compressed, say so in compression. A gzipped NDJSON file is "encodingFormat": "application/fhir+ndjson" with "compression": "gzip", never application/gzip.

Each class lists the media types it accepts. Some formats have no registered media type. For those the schema uses a fixed convention rather than an invented x- type, and the class says which format the file is:

  • Genomics formats (FASTQ, SAM, VCF, BAM, CRAM, BCF) use text/plain for text and application/octet-stream for binary. BAM, CRAM and BCF compress internally, so they leave compression unset; a .fastq.gz or .vcf.gz sets it to gzip. Indexes are always binary.
  • Sensor signal formats such as EDF, WFDB and vendor formats, and PLY 3D models, are application/octet-stream.
  • JSON Lines is application/jsonlines, and Parquet is application/vnd.apache.parquet.

How the data was produced: measurementTechnique

Genomics, imaging and sensor files state the assay or technique that produced them in measurementTechnique, schema.org's term. Analysis depends on it, so it is required. Each family has its own list of values, and each value maps to a term in an ontology such as OBI, NCIT or SNOMED CT (see Standards and mappings). Sensor files give a list, since one recording can combine several techniques.

Class-specific fields

These fields are defined for data files only. Each class uses some of them; the family pages show which are required.

Subjects and sensitivity on a file

  • subjectIds lists the subjects a file contains, by the coded IDs in the sidecar's subject table. It is required for classes that hold one person per file, such as FHIR Bundles, C-CDA documents, clinical documents and facial images, and optional for multi-subject tables.
  • sensitivity overrides the batch's contains* flags for one file, in either direction. A file of a biometric class cannot set containsBiometricIdentifiers. See Sensitivity for how batch and file values combine.
  • wasDerivedFrom points to the files in the same batch a file was made from, such as the alignment used to call variants.
