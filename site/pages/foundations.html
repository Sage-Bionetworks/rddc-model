Foundations

The metadata sidecar uses JSON-LD, schema.org and Croissant. These standards support reading and writing sidecars.

Background for the format

The RDDC tool can generate sidecars without detailed knowledge of these standards. This page explains terms such as cr:FileObject and @context.

Why use standards

Shared standards give familiar names and structures to the parts of a sidecar:

  • fields such as contentUrl have a shared definition;
  • Croissant tools such as mlcroissant can read the standard fields;
  • RDDC only defines and maintains clinical-specific additions.

JSON-LD: linked data

JSON-LD (JSON for Linked Data) connects JSON keys to shared definitions. A key such as "name" gets a unique identifier called an IRI. Documents that use the same IRI refer to the same term.

Four JSON-LD keywords

KeywordPurposeIn a sidecar
@contextA dictionary that maps short keys to IRIs.An embedded object at the top, copied unchanged from the generated context file.
@idA unique object identifier used by references.The sidecar's and every file's urn:uuid:…; short local IDs for file sets and record sets.
@typeThe object's type.sc:Dataset, cr:FileObject, cr:FileSet and a few others.
{"@id": …}A reference to another object by its ID.Linking a file set to its files, an index to its BAM, a field to its source file.

Context example

This JSON-LD example maps name to https://schema.org/name and defines the sc prefix.

{ "@context": { "@vocab": "https://schema.org/", "sc": "https://schema.org/", "cr": "http://mlcommons.org/croissant/" }, "@type": "sc:Dataset", "@id": "https://example.org/datasets/clinic-visits", "name": "Clinic visits" }

The sidecar uses two concepts:

  • Prefixes (CURIEs). sc:Dataset is short for https://schema.org/Dataset, and cr:FileObject for http://mlcommons.org/croissant/FileObject. The sidecar also uses rddc: (https://w3id.org/rddc/sidecar/), prov: and dct:.
  • A default vocabulary. @vocab means that any key without its own mapping is read as a schema.org term. That is why so many sidecar keys, such as name, url and dateCreated, need no prefix.
Reading a sidecar as plain JSON

An ordinary JSON parser can read a sidecar. The RDDC validator uses JSON Schema. Linked-data tools such as mlcroissant also use the context to interpret the fields.

schema.org: the shared vocabulary

schema.org defines terms for structured data on the web. The sidecar uses its Dataset type and these properties:

Croissant: loadable datasets

Croissant is a metadata format from MLCommons. It extends schema.org's Dataset with the details software needs to find, check and load data files. The mlcroissant Python library reads this format.

The sidecar follows Croissant 1.1. Croissant organizes a description into four layers. The sidecar uses the first three.

Layer 1: dataset metadata

Ordinary schema.org properties on an sc:Dataset: name, description, URL, creation date, license, and a conformsTo value specifying the Croissant version.

Layer 2: resources

The distribution list describes the actual files, using two Croissant classes:

  • cr:FileObject: one file, with contentUrl, contentSize, encodingFormat and a checksum.
  • cr:FileSet: a group of files selected by glob patterns in includes (and optionally excludes), such as every CSV in a folder.

Layer 3: structure

A cr:RecordSet describes a table's structure. Each cr:Field defines a column's data type, source file and column, and optional foreign-key references.

Layer 4: ML semantics (not used)

Croissant also defines ML-specific types, such as cr:Split for training, validation and test splits, cr:Label, cr:BoundingBox and cr:SegmentationMask. The specification marks them as experimental. The sidecar describes data at intake, not ML training sets, so it does not use them.

A small Croissant dataset

This example describes one CSV file with two columns in Croissant. Its context is shortened for readability. The same fields appear in an RDDC sidecar.

{ "@context": { "@vocab": "https://schema.org/", "sc": "https://schema.org/", "cr": "http://mlcommons.org/croissant/", "dct": "http://purl.org/dc/terms/", "conformsTo": "dct:conformsTo", "recordSet": "cr:recordSet", "field": "cr:field", "dataType": { "@id": "cr:dataType", "@type": "@vocab" }, "source": "cr:source", "fileObject": "cr:fileObject", "extract": "cr:extract", "column": "cr:column" }, "@type": "sc:Dataset", "conformsTo": "http://mlcommons.org/croissant/1.1", "name": "clinic-visits", "description": "Outpatient visit counts by month.", "license": "https://creativecommons.org/licenses/by/4.0/", "url": "https://example.org/clinic-visits", "distribution": [ { "@type": "cr:FileObject", "@id": "visits.csv", "name": "visits.csv", "contentUrl": "https://example.org/clinic-visits/visits.csv", "encodingFormat": "text/csv", "sha256": "5e0bd1a5b2c4f86f2b9e0b3c1d2a4e6f8091a2b3c4d5e6f708192a3b4c5d6e7f" } ], "recordSet": [ { "@type": "cr:RecordSet", "@id": "visits", "name": "visits", "field": [ { "@type": "cr:Field", "@id": "visits/month", "name": "month", "dataType": "sc:Date", "source": { "fileObject": { "@id": "visits.csv" }, "extract": { "column": "month" } } }, { "@type": "cr:Field", "@id": "visits/count", "name": "count", "dataType": "sc:Integer", "source": { "fileObject": { "@id": "visits.csv" }, "extract": { "column": "count" } } } ] } ] }

Enable Term origins in the header to see vocabulary colours: blue keys come from schema.org and amber keys from Croissant. On the RDDC pages a third colour, teal, marks the terms the RDDC adds.

What Croissant does not cover

The RDDC adds fields for clinical intake that the Croissant core does not define:

  • who the data is about, or how to withdraw one person's data later;
  • whether the batch carries data, a withdrawal, a restriction or consent;
  • clinical standards such as FHIR, OMOP or C-CDA and their versions;
  • de-identification facts, such as whether a file contains dates or faces;
  • pipeline provenance in a form that matches how the RDDC stores it.

RDDC and Croissant compares the standard fields with the RDDC additions.

W3C PROV: data provenance

PROV-O is the W3C vocabulary for recording where data came from. It describes entities such as files, activities such as pipeline runs, and the agents responsible for them. The sidecar uses two terms, shown in plum:

  • wasAttributedTo: the tool that wrote the sidecar;
  • wasDerivedFrom: source files or file sets within the same batch.

LinkML: schema definition

schema/rddc_sidecar.yaml defines the sidecar's fields, types and rules in LinkML. That file generates the JSON Schema, JSON-LD context and schema reference. Propose changes to the model in the YAML file.
