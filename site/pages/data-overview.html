How data is classified

Every data file the RDDC accepts belongs to one data class. The class says what kind of data the file holds, how to describe it, and what that means for processing and de-identification.

One class per file

Each file is described by a short set of fields: its path, size, media type and checksum, and a few more depending on the data. One of them, additionalType, names the file's RDDC data class, such as rddc:FhirNdjsonFile or rddc:SequenceReadsFile. The class decides:

  • which media types the file may have in encodingFormat;
  • which other fields it must or may carry, such as a FHIR resource type, a sequencing assay or a reference genome;
  • a set of facts about the data that every file of the class shares, described below.

The examples in this part show a file's fields as YAML, to keep the focus on the data; a field that points to another file, such as pairedWith, just gives that file's ID. Part 2 shows how the same fields are written for a deposit.

The classes form a hierarchy under DataFile, shown in full on the Data class reference. Abstract classes such as GenomicsFile group shared fields; a file always names a concrete class.

What the class says about the data

Some facts follow from the kind of data, so they belong to the class rather than to each file. They are annotations on the class in the schema, and a file never states them: the platform reads them from the class.

Modality
The kind of data, such as clinical_fhir, genomics or imaging. The platform uses it, together with the standard the data follows, to decide how to process the file. Each class has exactly one modality, so a new kind of data gets a new class rather than a new modality on an existing one.
Structure
structured data has defined fields that software can read without text or image analysis: FHIR, OMOP and other tables, C-CDA, VCF, FASTQ. unstructured data, such as notes, scans, images and recordings, needs NLP, OCR or image analysis. mixed classes admit either, so the file decides.
Collection type
How the data was collected, using the Croissant Responsible AI (RAI) term rai:dataCollectionType. Classes whose data always comes from an instrument (genomics, imaging and sensor data) are Direct measurement. Other classes leave it open, since a table or a document can come from many sources.
Biometric and identifying
Whether the content can identify a person on its own. See below.

The modalities

Files that identify a person

Removing names, record numbers and other direct identifiers is not enough to de-identify some kinds of data. Two class annotations mark them:

Identifying
The content can identify a person on its own. Genome sequences, alignments and variant calls are identifying: W3C DPV classes them as genetic data (pd:Genetic). A file of an identifying class never counts as de-identified, whatever its sensitivity flags say.
Biometric
The content is a biometric identifier under HIPAA Safe Harbor, such as a full-face image. Every file of a biometric class counts as containing biometric identifiers and stays in the trusted research environment (TRE). Biometric implies identifying. Since the class already says so, a facial image file cannot set containsBiometricIdentifiers itself; the schema rejects it.

Other files can contain biometric identifiers too, depending on their content. A voice recording, or a video that shows a face, sets containsBiometricIdentifiers to true in the file's sensitivity. The sensitivity flags list what each flag covers and the HIPAA Safe Harbor identifiers it corresponds to.

What a file does not state

A file states only what is particular to it. Anything known from elsewhere is left out, so it cannot contradict its source. The schema rejects these on a data file:

Not stated on the fileWhere it comes from
Modality, structure, collection type, biometric or identifyingThe file's class
FHIR version and implementation guides (such as US Core)The FHIR export or bundle collection the file belongs to
C-CDA release and template IDsThe document set the file belongs to, and the document header
A table name for a registry tableThe file's name and contentUrl

Choosing a class

Pick the most specific class that fits. In particular:

  • Data in a clinical standard (FHIR, OMOP CDM, C-CDA) uses that standard's class, even when it holds device data or patient-reported outcomes.
  • Consent tables are ConsentFiles and data dictionaries are DocumentationFiles, not TabularFiles: the platform handles them differently.
  • A photograph or 3D scan of a person's face is a FacialImagingFile, not an ImagingFile.
  • Raw sensor signals and measures derived from them are different classes, SensorSignalFile and SensorMeasureFile.
  • When nothing fits, use GenericFile. A curator decides how it is processed, and a kind of data the RDDC receives regularly gets its own class in a later schema version.
