How data is classified

Every data file the RDDC accepts belongs to one data class. The class defines the file's content and format, its metadata fields, and what processing and de-identification it needs.

One class per file

Each file specifies its path, size, media type, checksum and any class-specific fields. One of them, additionalType, names the file's RDDC data class, such as rddc:FhirNdjsonFile or rddc:FastqFile. The class decides:

  • which media types the file may have in encodingFormat;
  • its required and optional fields, such as a FHIR resource type, a sequencing assay or a reference genome;
  • annotations shared by all files in the class, described below.

The examples in this part show a file's fields as YAML, to keep the focus on the data; a field that points to another file, such as pairedWith, just gives that file's ID. Part 2 shows how the same fields are written for a deposit.

The classes form a hierarchy under DataFile, shown in full on the Data class reference. Abstract classes such as GenomicsFile group shared fields; a file always names a concrete class.

Class and format

A concrete class is what one processing pipeline consumes. Where the pipeline depends on the format and a media type cannot tell the formats apart (BAM and CRAM, EDF and other sensor formats), or the pipelines differ by format (FASTQ and unaligned BAM, DICOM and other image formats), the format is the class, and the class maps to its EDAM format term. Elsewhere one class covers the formats and encodingFormat and compression say which: FHIR JSON and NDJSON, CSV and Parquet, and the variant call formats VCF, BCF and MAF, whose classes are decided by what they contain, germline or somatic variants.

Processing rules match a class together with all its subclasses, so a subclass must be processable as its parent; what differs between siblings, such as whether they identify a person, is in their annotations, which the rules read per concrete class. A facial image is not a subclass of the image classes, since the header de-identification and analysis of medical images do not apply to it.

Class annotations

Class annotations define shared characteristics. These class characteristics are defined by our model and are not fields to be filled in.

Modality
The kind of data a source registers to deposit, such as clinical_fhir, genomics or sensor. The platform checks a file's modality against the source register; how the file is processed follows from its class. Each class has exactly one modality, so a new kind of data gets a new class rather than a new modality on an existing one.
Structure
structured data has defined fields that software can read without content analysis: FHIR, OMOP and other tables, C-CDA, VCF, FASTQ. Free text inside such a file is declared with containsFreeText. unstructured data, such as notes, scans, images and recordings, has no fields: any identifier in it can only be found by NLP, OCR or image or audio analysis. mixed classes allow either structure, depending on the file's content.
File set class
The file set every file of the class belongs to: an OmopTableFile in an OmopCdmInstance, a FhirNdjsonFile in a FhirBulkExport. The set's conformsTo gives the standard and version the files follow, so the files do not repeat it.
Collection type
How the data was collected, using the Croissant Responsible AI (RAI) term rai:dataCollectionType. Classes whose data always comes from an instrument (genomics, imaging and sensor data) are Direct measurement. Other classes leave it open, since a table or a document can come from many sources.
Biometric and identifying
Whether our model automatically treats every file in the class as identifying, regardless of sensitivity flags. See below.
Sensitivity flags
What the class says about each contains* flag: fixed for every file, a default, or left to the batch. See below.

Depends on content means the class alone does not determine whether a file is identifying. FHIR files, for example, may contain identifying information and still require de-identification checks. The absence of a class annotation does not mean a file is de-identified.

Modalities

Identifying files

Removing names, record numbers and other direct identifiers is not enough to de-identify some kinds of data. Two class annotations mark them:

Identifying
Our model automatically treats files in these classes as identifying, even after direct identifiers are removed. Genome sequences, alignments and variant calls are identifying: W3C DPV classes them as genetic data (pd:Genetic). A file of an identifying class never counts as de-identified, regardless of sensitivity flags.
Biometric
The content is a biometric identifier under HIPAA Safe Harbor, such as a full-face image. Every file of a biometric class counts as containing biometric identifiers and never leaves INTAKE: it is not loaded into the normalized store or released. Biometric implies identifying. Since the class already says so, a facial image file cannot set containsBiometricIdentifiers itself; the schema rejects it.

Other files can contain biometric identifiers too, depending on their content. A voice recording, or a video that shows a face, sets containsBiometricIdentifiers to true in the file's sensitivity. The sensitivity flags list what each flag covers and the HIPAA Safe Harbor identifiers it corresponds to.

Sensitivity flags by class

A flag that nothing sets is unknown and treated as true, which would hold every file for review. The class narrows that where the format decides:

  • always: every file of the class has it, so a file cannot set the flag. A clinical document is free text.
  • n/a: the format cannot carry it, so the flag is false and a file cannot set it. A FASTQ holds no dates.
  • false unless set: the value when neither the file nor the batch sets the flag. An OMOP table has no column for a photograph.
  • batch value: the file's own setting, else the batch's, else unknown.

In order, a flag's value for a file is what its class fixes, what the file sets, what the batch sets, the class default, else unknown.

Choosing a class

Pick the most specific class that fits. In particular:

  • Data in a clinical standard (FHIR, OMOP CDM, C-CDA) uses that standard's class, even when it holds device data or patient-reported outcomes.
  • Consent tables are ConsentFiles and data dictionaries are DocumentationFiles, not TabularFiles: the platform handles them differently.
  • Reads, alignments, raw sensor signals and images name their format: CramFile, not a generic alignment class; EdfSignalFile; DicomImageFile or ImageFile. Variant calls name their content, GermlineVariantFile or SomaticVariantFile.
  • Intake form responses are IntakeFormFiles read with the form's definition, structured genetic test results are GeneticTestResultFiles, and a diagnosis support tool's ranked candidates are a DifferentialDiagnosisFile, not TabularFiles.
  • A photograph or 3D scan of a person's face is a FacialImagingFile, not an image class.
  • Raw sensor signals and measures derived from them are different classes: one of the signal classes, or SensorMeasureFile.
  • GenericFile is strongly discouraged. A dedicated data class is required; using GenericFile triggers lengthy manual review.
