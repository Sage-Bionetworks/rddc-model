Lifecycle and validation

Metadata sidecar preparation, upload, validation and processing.

Processing lifecycle

  1. Draft

    The contributor runs the generator on the batch directory. It identifies file types, computes checksums, extracts subject IDs, proposes file sets and assigns file IDs, recording the origin of every value it fills in.

  2. Validate locally

    The validator checks the sidecar against the schema and the files on disk, offline. The contributor confirms or corrects any inferred values. This matters because delivery credentials are write-only: once uploaded, nothing can be changed.

  3. Upload

    Data files first, then _sidecar.json, all under one batch prefix in the contributor's bucket.

  4. Receive

    The sidecar's arrival starts one receipt workflow for the batch. It checks the delivery role and sourceId, waits for every listed file, verifies checksums, reports objects missing from either side, checks subjects against the participants table, and registers the files in Synapse with sidecar fields as annotations.

  5. Screen

    De-identification and QC tasks pick their checks from each file's format and sensitivity flags. Exceptions go to curators with the file and subject context from the sidecar.

  6. Process

    The NORMALIZE stage selects a processing path from each file's modality (set by its class) and the file set's conformsTo, reads task parameters from the file and file-set fields, and verifies inputs by checksum.

  7. Register outputs

    Synapse registers pipeline outputs with the provenance recorded in Cirro, in W3C PROV form. Outputs do not get sidecars; the sidecar describes the deposit only.

Validation checks

Intrinsic checks use the sidecar, files and schema and give the same result wherever they run. Registry checks compare source details with the local source descriptor or the live source register. Participant checks run at receipt.

The JSON Schema generated from the model covers the schema and vocabulary checks. The RDDC validator handles the remaining checks; the reference lists the rules JSON Schema can't express.

Reading a validation report

Each finding includes a severity, rule ID, JSON pointer, file and message. Tools can read the report to suggest fixes. Errors block processing; warnings do not.

{ "severity": "error", "rule": "integrity.checksum_mismatch", "path": "/distribution/12/sha256", "contentUrl": "omop/person.csv", "message": "sha256 does not match the file" }

path is a JSON pointer into the sidecar; contentUrl is present when the finding concerns a file. The command exits with 0 when there are no errors, 1 when there are, and 2 when the sidecar or directory can't be read.

Immutability

Once received, a sidecar cannot be edited. The platform stores identifiers such as Synapse IDs in its own metadata. Correction and resubmission workflows are still being designed.

Schema versioning

  • The schema follows semantic versioning. Minor versions only add optional fields or enumeration values. Adding a required field, removing a field or value, or changing a type needs a major version.
  • Each sidecar declares its schema version in conformsTo, such as https://w3id.org/rddc/sidecar/{{version}}, and is validated against that version. A value deprecated later stays valid for sidecars that declare an earlier version.
  • Within a major version, a sidecar valid under x.y is valid under every later x.z.
  • Validators accept the current and previous major version for a deprecation window, proposed as two quarters.
  • Releases are git tags named v<major>.<minor>.<patch>. Tools pin a tag, never the default branch.
