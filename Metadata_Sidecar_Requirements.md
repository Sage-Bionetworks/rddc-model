# Metadata Sidecar — Requirements

Oct 27, 2026 · @Anh Nguyet Vu · Status: Draft

## Overview

Every file set (one submission, or one S3 prefix) gets a single machine-readable manifest sidecar that describes all its files and how they relate, so pipelines can process them without looking anything up elsewhere. The manifest is the contract between data producers and processing: if a pipeline needs a value to decide what to do with a file, that value is in the file's manifest entry.

The manifest complements, not replaces, metadata held in the platform (e.g. annotations). It is optimized for automated consumers first and human curators second.

## Scope

**In scope**

- Manifest format, location, and naming within a file set
- Per-file entries: identity, checksums, and the fields needed to route, process, and validate data
- Links between files: membership, spec conformance (FHIR, OMOP), relational keys, and provenance
- Schema definition, validation, and versioning of the manifest
- How pipelines read manifests and emit new ones for derived outputs
- Tooling that generates manifests, and ingest of file sets uploaded directly to S3

**Out of scope**

- Replacing platform-level annotations or the data model's source of truth
- Storage of the data files themselves
- Study-level or project-level metadata that is not needed per file
- Access control for manifests themselves, which is set by platform policy

**Assumptions**

- One manifest per file set (a submission or prefix), never one per bucket; the bucket-wide view is assembled in the registry or graph
- Manifests are usually generated by tooling
- Collaborators may upload with standard AWS tooling (`aws s3 sync`), so the manifest travels as an ordinary file in the set
- Field definitions come from the governed data model, not from the manifest spec

## Users and consumers

Processing pipelines are the primary consumer.

| Consumer | Uses the manifest to | Priority |
| --- | --- | --- |
| Processing pipelines | Route files, pick parameters, check preconditions, emit manifests for derived outputs | Primary |
| Data contributors | Create the original manifest, and upload it to signal that a data deposit is complete and ready for processing | High |
| Curators | Review, correct, and validate metadata before release | High |
| Portals and search | Index and filter files | Medium |
| AI and agentic tooling | Read context about a file without platform calls | Medium |

## Functional requirements

MoSCoW priority: M = must, S = should, C = could.

| ID | Requirement | Priority | Notes |
| --- | --- | --- | --- |
| FR-1 | Each file set is described by exactly one manifest, discoverable from the file set's location, with one entry per file | M | E.g. a fixed name at the set's root, such as `_manifest.json`. Depends on how a file set is bounded (open question) |
| FR-2 | The manifest uses an open, widely supported format that can be read without custom libraries | M | Candidates: JSON header with JSON Lines or Parquet entries; see NFR-1 |
| FR-3 | The manifest declares the schema name and version it conforms to | M | Same pattern as Croissant `conformsTo` |
| FR-4 | Each file entry records the file's location within the set, its size, and its checksums, each checksum with its algorithm, so manifest and files can be reconciled | M | Algorithm required so values are verifiable |
| FR-5 | Every field a pipeline branches on is present and typed, never free text | M |  |
| FR-6 | Each file entry carries a stable identifier that persists across moves and manifest versions, distinct from any collaborator-supplied IDs, which are kept as aliases | M | E.g. minted by a registry; where it lives is an open question |
| FR-7 | Manifests for derived outputs reference the identifiers of their input files | M | Depends on FR-6 |
| FR-8 | Manifests can be validated standalone, offline, before upload | M |  |

## Content and schema

The manifest has a header stated once for the set, an entry per file, and a links section. Processing-critical fields are required; descriptive fields are optional. The model follows the file-set pattern of Croissant and Frictionless Data Packages.

| Part | Fields (examples) | Required |
| --- | --- | --- |
| Header | `schema`, `schema_version`, `manifest_id`, `created_at`, `generated_by`, `supersedes`, `file_set_location` (bucket + prefix) | Yes |
| File entry: identity | `file_id`, `key` (relative to the set), `file_format`, `size_bytes`, `checksums` (algorithm + value each), `external_ids` | Yes |
| File entry: processing | `data_type`, `assay`, `platform`, `reference_genome`, `pipeline_hints` | Yes, per data type |
| File entry: biospecimen and subject | `specimen_id`, `individual_id`, `tissue`, `diagnosis` | Per data type |
| File entry: provenance | `derived_from` (input `file_id`s), `pipeline`, `pipeline_version`, `parameters` | Yes for derived files |
| Access and sensitivity | `access_level`, `contains_phi`, `consent_codes`, set on the header with per-file overrides | Yes |
| Links | Membership, conformance, relational keys (next section) | When files relate |
| Extensions | Namespaced, project-specific fields | No |

- Controlled fields use terms from the governed vocabulary, stored as both label and CURIE (e.g. ontology ID)
- Required fields vary by `data_type`, expressed as conditional rules in the schema
- Values shared by every file (e.g. study, assay) sit on the header and are inherited by entries unless overridden
- The schema is defined in LinkML (NFR-7); artifacts such as JSON Schema are generated from it

### Links between files

The links section describes how files in the set belong together. Where a spec already defines how the parts link (FHIR, OMOP), the manifest points to that spec instead of restating it. A set can hold several groups, e.g. one FHIR export and one OMOP instance.

| Link kind | What it records | Example |
| --- | --- | --- |
| Membership | Member file entries and each member's role | OMOP table name; FHIR resource type per NDJSON file |
| Conformance | Spec and version the collection follows | OMOP CDM 5.4 + vocabulary release; FHIR R4 + implementation guide |
| Relational keys | Joins between members, only when no spec defines them | `samples.csv:specimen_id` → `assays.csv:specimen_id` |
| Provenance | Collection-level derivation | OMOP instance derived from a FHIR bulk export |

- **FHIR:** references live inside the records, so the group records resource type per file, export time, and FHIR version; the Bulk Data export manifest maps in directly
- **OMOP:** foreign keys are fixed by the CDM spec, so the group records which tables are present, CDM and vocabulary versions, and `cdm_source` details
- Validators use the declared spec and version to check that expected members and keys are present
- Candidate LinkML classes: `FileSetManifest` (header + provenance mixins), `FileEntry`, `FileGroup` (with a `GroupTypeEnum`: `fhir_bulk_export`, `omop_cdm_instance`, `file_set`), and `FileLink` for ad hoc keys

## Processing integration

A pipeline must be able to start from a manifest alone and finish by writing one. The lifecycle runs in a straight line:

1. **Create.** The manifest is drafted before upload, and each file is assigned a stable `file_id`.
2. **Upload.** The collaborator uploads the files and the manifest together, through any supported path (e.g. the generator, the Synapse client, or `aws s3 sync`).
3. **Ingest.** On arrival, objects are paired with the manifest by location and checksum, and validated; each file's identity and location are then available for registration. Objects missing from the manifest are reported.
4. **Discover.** Pipelines find work by querying registered entries (e.g. all `data_type = RNA-seq` files without a derived output).
5. **Process.** The pipeline reads parameters from the file's entry, and the entry's checksum lets it verify the file before use.
6. **Emit.** Each run writes its own manifest for its outputs, with `derived_from` pointing to input `file_id`s.
7. **Sync.** Manifest fields can be mapped to platform annotations, so portals and search can see them (FR-10).

What the manifest enables for pipelines:

- Entries carry every field a pipeline needs to run, so a missing value can fail fast rather than be guessed
- Manifests are immutable once consumed, so pipelines never need to change an input manifest (see Versioning)
- Shared tooling gives every pipeline the same manifest reading and writing behavior
- Manifest output is deterministic, so the same inputs and parameters can yield an identical output manifest, apart from timestamps

## Validation and quality

Validation runs at three gates with the same rules.

| Gate | When | On failure |
| --- | --- | --- |
| Local | Collaborator runs the CLI before upload | Error report, upload blocked |
| Ingest | The manifest and objects land in S3 or Synapse | Error report names the failing files and fields |
| Pre-processing | Pipeline reads a file's entry | Error names the failing field, so the job can fail fast |

Checks, in order:

1. Syntax: valid JSON (header) and JSON Lines or Parquet (entries), UTF-8
2. Schema: types, required fields, conditional rules by `data_type`
3. Vocabulary: controlled terms resolve to current, non-deprecated IDs
4. Reconciliation: every object in the prefix has an entry and every entry has an object, checkable at ingest or any time after
5. Integrity: checksums match the objects; referenced `file_id`s exist
6. Consistency: values agree across entries (e.g. same `individual_id` maps to one diagnosis)

Validation errors are machine-readable (field path, rule, message) so tools and AI assistants can suggest fixes.

## Manifest generation tooling

A generator drafts the file set's manifest by detecting file types and relations. Detected values never silently stand in for a required field.

| Layer | Method | Examples | Confidence |
| --- | --- | --- | --- |
| Checksums | Computed in the same pass that reads the file | MD5 (platform compatibility) + SHA-256, each stored with its algorithm | Exact |
| File type | Magic bytes, headers, content sniffing | gzip, BAM/CRAM, VCF, FASTQ, Parquet; NDJSON with `resourceType` = FHIR; CSV columns matching an OMOP table, including CDM version | High |
| Embedded metadata | Parse format headers | BAM `@RG`/`@PG` → read groups, producing pipeline; VCF `##reference` → genome build | High |
| Spec-defined relations | Resolve against the declared spec | FHIR `Patient/123` references across files; OMOP foreign keys checked against the CDM | High |
| Conventions | Filename and pairing patterns | R1/R2 reads; `.bai` beside `.bam`; sample IDs in names | Medium |
| Ad hoc relations | Shared column names + value overlap | Candidate key between two CSVs | Low, needs confirmation |
| Vocabulary terms | LLM suggestion for free-text fields | Free-text tissue → ontology term | Flagged for review |

- Each auto-filled value records its origin (`detected` or `declared`), detection method, and confidence
- Sensitivity fields (`contains_phi`, `access_level`) default to the most restrictive value and are never auto-set to permissive
- Drafts pass through the same validator as hand-made manifests; `generated_by` records the tool and its version
- The generator runs as a CLI and a library, over single files, directories, or collections

## Versioning, provenance, and lineage

Two things are versioned separately: the schema and each manifest.

- **Schema versions** follow semantic versioning. Minor versions only add optional fields; a major version is required to add a required field, remove a field, or change a type.
- **Validators** accept the current and previous major version for a defined deprecation window.
- **Manifests** are immutable once a pipeline has consumed them. A correction writes a new manifest with `supersedes` pointing to the old one; adding files to a set does the same.
- **File identity** survives moves and new manifest versions: the same bytes keep the same `file_id`, while changed content gets a new entry that supersedes the old one.
- **Lineage** is captured through `derived_from`, so any output can be traced back to raw inputs by walking manifests alone.
- Provenance fields should map cleanly to a standard model (e.g. W3C PROV) so lineage can be loaded into a knowledge graph.
- Migration tooling upgrades manifests across major schema versions without manual edits.

## Non-functional requirements and security

| ID | Requirement | Priority | Notes |
| --- | --- | --- | --- |
| NFR-1 | A manifest supports at least 100,000 file entries and can be read incrementally | M | Drives the format choice in FR-2; large per-file data (e.g. QC arrays) could live in referenced files |
| NFR-2 | Validating 10,000 entries takes under 5 minutes | S | See note below |
| NFR-3 | A CLI reads, writes, and validates manifests | M | Works from any pipeline language via shell calls |
| NFR-4 | Manifests never contain direct identifiers or PHI; only coded IDs | M |  |
| NFR-5 | Schema, validator, and library are open source and documented with examples per data type | S |  |
| NFR-6 | A Python library exposes the same read, write, and validate functions as the CLI | S | The CLI can be a thin layer over it |
| NFR-7 | The manifest schema is defined in LinkML | M | Already specified in the infrastructure plan |

Numeric targets are starting points to confirm with pipeline owners.

## Open questions

- [ ] Is the manifest or the platform annotation the source of truth when they disagree?
- [ ] What bounds a file set: one submission, one prefix, or either?
- [ ] Do we adopt Croissant or Frictionless Data Package as the manifest's base, or define our own and map to them?
- [ ] Which group specs and versions are supported first (e.g. FHIR R4, OMOP CDM 5.4)?
- [ ] Do we store FHIR and OMOP files as-is, or validate them against their spec at ingest?
- [ ] Are MD5 + SHA-256 the right default digests, or is one enough?
- [ ] Where does the `file_id` registry live (DynamoDB, the graph, Synapse), and do we expose it through GA4GH DRS?
- [ ] Which data types are in the first release, and who owns each type's required-field rules?
- [ ] How long is the deprecation window for old schema major versions?
- [ ] Who approves new extension namespaces?
