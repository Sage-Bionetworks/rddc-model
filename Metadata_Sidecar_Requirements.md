## Overview

Every deposit (one **batch** of files for one **source**, written under one S3
prefix in the contributor's bucket) carries a single machine-readable
**metadata sidecar** that describes the batch, lists its files and how they
relate, and lists the subjects whose data it contains. The sidecar is the
deposit contract between data contributors and the RDDC INTAKE module: its
arrival triggers batch receipt, and if a downstream step needs a value to
decide what to do with a file, that value is in the sidecar.

The sidecar has two parts, following the plan's definition:

- the **manifest**: batch identity and one entry per file with location,
  checksums, modality and conformance, plus the links between files;
- the **subject table**: one row per subject ID present in the deposit, used
  for the participants-table check, for withdrawals, and for consent batches.

The sidecar complements, not replaces, metadata held in the platform (the
source register, the batch register, Synapse annotations). It is optimized for
automated consumers first and human curators second.

## Terminology

Taken from the Infrastructure Plan, Appendix A.

| Term | Meaning |
| --- | --- |
| Contributor | An organization that sends data. Has one bucket and one or more sources. |
| Source | One data set of one contributor with one set of use terms. Registered in the source register before the first deposit. |
| Batch, deposit | One delivery of files for one source. One batch, one prefix, one sidecar. |
| Manifest | The part of the sidecar that lists the files of the batch. |
| Subject table | The part of the sidecar that lists the subject IDs in the batch. |
| Subject ID | The contributor's ID for a person. Not a name, MRN or other direct identifier. Appears in the data, the sidecar and the identifier map; never in a release. |
| Lane | The NORMALIZE path for one input format: 1 OMOP load, 2 FHIR, 3 C-CDA, 4 registry/PRO/claims/mortality tables via Netrias. |

## Scope

**In scope**

- Sidecar format, location, naming and upload order within a batch
- Batch identity: contributor, source, batch, payload interaction type
- Per-file entries: identity, checksums, modality, format, conformance, and the typed fields needed to route, process and validate data
- Subject table and per-file subject references
- Links between files: membership, spec conformance (FHIR, OMOP, C-CDA), relational keys, and provenance
- Sensitivity facts needed by de-identification and routing
- Schema definition, validation and versioning of the sidecar
- How pipelines read sidecars and emit new ones for derived outputs
- Tooling that drafts, validates and normalizes sidecars, and the receipt of batches uploaded directly to S3

**Out of scope**

- Use terms, access tier, de-identification class, date policy and delivery role: these live in the source register and are set by the ACT (plan §7.2, §7.6)
- De-identification and QC tests themselves: these are Cirro tasks that read the sidecar (plan §3.2)
- Storage, encryption and credentials for the data files
- Study-level or project-level metadata not needed per batch or per file
- Access control for the sidecar object itself

**Assumptions**

- One sidecar per batch, never one per bucket; the bucket-wide view is assembled in the batch register
- Sidecars are usually generated by tooling, but a hand-written sidecar that validates is equally acceptable
- Contributors upload with standard AWS tooling (`aws s3 sync`, the Synapse client, or the generator), so the sidecar travels as an ordinary object in the prefix
- Delivery credentials are **write-only** (plan §3.2): the contributor cannot list, read back, overwrite or delete objects. Everything the contributor needs to check must therefore be checkable locally before upload, and corrections are new sidecars, not edits
- Field definitions and controlled vocabularies come from the governed LinkML data model; the sidecar schema is a module of it

## Functional requirements

MoSCoW priority: M = must, S = should, C = could.

Requirements are split in two. **Part A** specifies the sidecar model: the
document contract that any producer must satisfy and any consumer can rely on,
whatever tool wrote it. **Part B** specifies the accompanying tooling: the
generator, validator and library the RDDC provides so that contributors and
pipelines meet Part A without hand work. A sidecar written by hand or by a
third-party tool is as valid as one from the reference tooling, provided it
meets Part A.

## Content and schema

The sidecar has a **header** stated once for the batch, a **subject table**, a
**manifest** (file entries), a **groups** section and a **links** section.
Processing-critical fields are required; descriptive fields are optional. The
model follows the file-set pattern of Croissant and Frictionless Data Packages
and is defined in LinkML (NFR-7); JSON Schema and Pydantic classes are generated
from it.

| Part | Fields (examples) | Required |
| --- | --- | --- |
| Header: schema | `schema_name`, `schema_version`, `sidecar_id`, `created_at`, `generated_by` (tool, version), `supersedes` | Yes |
| Header: batch | `contributor_id`, `source_id`, `batch_id`, `interaction`, `location` (bucket, prefix), `description` | Yes |
| Header: sensitivity | `direct_identifiers_removed`, `contains_dates`, `contains_zip_codes`, `contains_free_text`, `contains_biometric_identifiers`, `synthetic` | Yes |
| Header: companions | `files_ref`, `subjects_ref` with checksums, when entries are externalized | When used |
| Source descriptor (separate file, FR-28) | `contributor_id`, `source_id`, `bucket`, `prefix_pattern`, `modalities`, `register_version`, `issued_at`, `issued_by` | Issued per source |
| Subject table | `subject_id`, `id_system`, `consent_ref` | Yes for `upsert`, `withdraw`, `restrict`, `consent` |
| File entry: identity | `file_id`, `key`, `size_bytes`, `checksums`, `media_type`, `external_ids` | Yes |
| File entry: processing | `modality`, `file_format`, `subject_ids`, `processing_hints` (namespaced key–value, informational) | Yes per modality |
| File entry: sensitivity | Same flags as the header, as overrides | Optional |
| File entry: provenance | `derived_from` (input `file_id`s), `pipeline`, `pipeline_version`, `parameters`, `run_id` | Yes for derived files |
| File entry: origins | `value_origins`: field, origin, method, confidence, confirmed | Yes for auto-filled values |
| Group | `group_id`, `group_type`, `conformance` (standard, version, profiles, vocabulary_version, cdm_source), `members` (file_id, role, record_count), `export_time`, `derived_from_groups` | When files form a collection |
| Link | `from_file_id`, `from_field`, `to_file_id`, `to_field`, `link_type`, origin | When no spec defines the join |
| Extensions (proposed, FR-9) | Namespaced, project-specific fields (`ext:<namespace>:<key>`) | No |

Rules:

- Controlled fields use enumerations from the governed vocabulary; where a term has an ontology ID it is stored as both label and CURIE.
- Required fields vary by `modality` and `group_type`, expressed as conditional rules in the schema.
- Precedence for values stated at more than one level: file entry, then group, then header. Validators report the effective value.
- `processing_hints` is informational. Anything a pipeline branches on must be a schema field (FR-5).

### Links between files

Where a spec already defines how the parts link, the group points to that spec. A batch can hold several groups, for example one FHIR bulk export, one OMOP instance and one document set.

| Link kind | What it records | Example |
| --- | --- | --- |
| Membership | Member entries and each member's role | OMOP table name; FHIR resource type per NDJSON file; `transaction` bundle |
| Conformance | Spec and version the collection follows | OMOP CDM 5.4 + vocabulary v5.0 25-AUG-2026; FHIR 4.0.1 + US Core 6.1.0 |
| Relational keys | Joins between members, only when no spec defines them | `visits.csv:patient_id` → `patients.csv:id` |
| Provenance | Collection-level derivation | OMOP instance derived from a FHIR bulk export |

- **FHIR:** references live inside the records, so the group records resource type per file, bundle type, export time and FHIR version; a Bulk Data `$export` status manifest maps in directly.
- **OMOP:** foreign keys are fixed by the CDM, so the group records which tables are present, CDM and vocabulary versions, and `cdm_source` details.
- **C-CDA:** one document per subject encounter; the group records the C-CDA release and template IDs.
- Validators use the declared spec and version to check that expected members are present (for OMOP, at least `person` and `observation_period`; for FHIR bulk, at least `Patient`).

## Processing integration

A pipeline must be able to start from a sidecar and finish by writing
one. The lifecycle follows the plan's INTAKE sequence (§3.2) and NORMALIZE
compute tasks (§4.2):

1. **Draft.** The contributor runs the generator over the batch directory; files are typed, checksums computed, subjects extracted, groups proposed, `file_id`s minted.
2. **Validate locally.** The validator checks schema, vocabulary, reconciliation against the directory, checksums, subject references and sensitivity attestations. Inferred values are confirmed or corrected.
3. **Upload.** Data objects first, then the sidecar, under one prefix in the contributor bucket, using the short-term write-only credentials.
4. **Receive.** The EventBridge rule on the sidecar object starts one receipt workflow per batch. It verifies the delivery role and `source_id`, waits for every listed object, verifies checksums, reports objects missing from the sidecar or the bucket, checks the subject table against the participants table, and registers files in Synapse (DRS references) with sidecar fields as annotations.
5. **Screen.** De-id and QC tasks run in Cirro, reading format and sensitivity facts from the sidecar. Exceptions go to curators with file and subject context.
6. **Process.** NORMALIZE picks the lane from modality and conformance, reads task parameters from the group and entries, and verifies inputs by checksum.
7. **Emit.** Each run writes its own sidecar for its outputs with `derived_from` pointing to input `file_id`s and `generated_by` naming the pipeline and version. Release manifests reuse the same schema.

The batch-folder JSON Schema that governs Synapse annotations (plan Table 4) is generated from the same LinkML model as the sidecar, so registration may apply the relevant subset of sidecar fields as annotations directly without a separate field mapping to maintain.

What this gives pipelines:

- Entries carry every field a pipeline needs
- Sidecars are immutable once received; pipelines never change an input sidecar
- Shared tooling gives every pipeline the same read, write and validate behavior
- Generator output is deterministic for the same inputs and options, apart from timestamps and `sidecar_id`

## Validation and quality

Validation rules are of two kinds:

- **Intrinsic** validation need only the sidecar, the files and the schema: syntax, schema, identity, reconciliation, integrity, references, subjects, sensitivity, conformance, confirmation. They run identically at every gate and are the whole of what a contributor can verify offline.
- **Registry** validation compare the sidecar with the registry database, which contains the known contribution sources (`contributor_id`, `source_id`, bucket, modalities, delivery role) and the participants table (subject IDs). This runs at receipt. Locally they run against the source descriptor when it is supplied (FR-28); when it is absent the validator passes with a warning that registry checks are deferred.

The gates, mapped to the plan's stages:

| Gate | Who | When | On failure |
| --- | --- | --- | --- |
| Local | Contributor CLI | Before upload | Error report; upload should not proceed. Intrinsic rules; registry rules against the source descriptor if present |
| Receipt | INTAKE workflow | Sidecar object lands | Batch stopped at receipt; report names failing files and fields (plan §3.2). Intrinsic rules plus registry rules against the live source register and participants table |
| Screening hand-off | De-id and QC tasks | Before tests run | Tasks fail fast on missing format or sensitivity facts |
| Pre-processing | NORMALIZE lane | Compute task reads an entry or group | Task fails naming the field |

Checks, in order:

1. **Syntax:** valid UTF-8 JSON; companion JSON Lines files parse line by line.
2. **Schema:** types, required fields, enumerations, conditional rules by `interaction`, `modality` and `group_type`; unknown fields rejected except inside the proposed extensions block (FR-9).
3. **Vocabulary:** controlled terms resolve to current, non-deprecated IDs.
4. **Identity:** `file_id`s unique; `supersedes` well-formed; `source_id` and `batch_id` well-formed.
5. **Reconciliation:** every object under the prefix (or local directory) has an entry and every entry has an object; companion files match their declared checksums.
6. **Integrity:** checksums match the objects; referenced `file_id`s and `group_id`s exist.
7. **Subjects:** per-file `subject_ids` resolve to the subject table; `withdraw`, `restrict` and `consent` have a non-empty subject table; subject IDs are not name-like.
8. **Sensitivity:** `direct_identifiers_removed` is true for non-synthetic data; tabular headers and object keys do not match known direct-identifier patterns (names, SSN, MRN, address, phone, email); media files flagged for biometrics.
9. **Conformance:** declared group type matches detected content; required members present for the declared standard; CDM version consistent across tables.
10. **Confirmation:** no unconfirmed `inferred` values remain.

11. **Registry:** `contributor_id`, `source_id` and bucket match the source descriptor (local) or the source register (receipt); the prefix matches the source's pattern; every file's `modality` is one the source is registered for; subject IDs resolve in the participants table (receipt only).

Validation errors are machine-readable (severity, rule ID, JSON pointer, file
key, message) so tools and AI assistants can suggest fixes. Exit status is
non-zero when any error remains; warnings do not block.

## Sidecar generation tooling

A generator drafts the sidecar by detecting file types, embedded metadata and
relations. Detected values never silently stand in for a required field: the
generator records where each value came from and leaves required fields it
cannot fill empty, which fails validation.

| Layer | Method | Examples | Confidence |
| --- | --- | --- | --- |
| Checksums | Computed in the same pass that reads the file | SHA-256 + MD5 | Exact |
| File type | Magic bytes, headers, content sniffing | JSON with `resourceType: Bundle`; NDJSON with one `resourceType` per file; CSV whose columns match an OMOP CDM 5.4 table; XML `ClinicalDocument` with C-CDA template IDs; gzip, BAM/CRAM, VCF, DICOM | High |
| Embedded metadata | Parse format headers | FHIR bundle type, resource counts, US Core profiles; OMOP `cdm_source` row; C-CDA template extension; BAM `@RG`/`@PG`; VCF `##reference` | High |
| Subjects | Extract per the declared spec | FHIR `Patient.id`; OMOP `person.person_source_value`; C-CDA `recordTarget` | High |
| Spec-defined relations | Resolve against the declared spec | FHIR references across NDJSON files; OMOP foreign keys against the CDM | High |
| Conventions | Filename and pairing patterns | Table name from file stem; R1/R2 reads; `.bai` beside `.bam` | Medium |
| Ad hoc relations | Shared column names + value overlap | Candidate key between two CSVs | Low, needs confirmation |

- Each auto-filled value records its origin (`detected`, `declared`, `inferred`), method and confidence in [0, 1].
- Sensitivity flags default to the most restrictive value and are never auto-set to permissive; `direct_identifiers_removed` must be declared by the contributor.
- Drafts pass through the same validator as hand-made sidecars; `generated_by` records the tool and its version.
- The generator runs as a CLI and a Python library, over a batch directory, and can carry `file_id`s forward from a previous sidecar.

## Versioning, provenance and lineage

Two things are versioned separately: the schema and each sidecar.

- **Schema versions** follow semantic versioning. Minor versions only add optional fields or enumeration values; a major version is required to add a required field, remove a field, or change a type.
- **Validators** accept the current and previous major version for a deprecation window (proposed: two quarters, to be confirmed).
- **Sidecars** are immutable once received. A correction, a rectification, or an addition of files is a new sidecar for a new batch with `supersedes` pointing to the earlier `sidecar_id`. The new sidecar lists every file of the batch; objects that are unchanged and still present need not be re-uploaded.
- **File identity** survives moves and new sidecar versions: the generator carries forward the `file_id` of any entry whose SHA-256 is unchanged; changed content gets a new `file_id`, and the entry records the one it supersedes.
- **Lineage** is captured through `derived_from`, so any output can be traced back to raw inputs by walking sidecars alone.
- **Provenance** fields map to W3C PROV (entity = file, activity = pipeline run, agent = pipeline or tool), matching how Synapse stores Cirro provenance (plan §4.3).
- **Migration** tooling upgrades sidecars across major schema versions without manual edits.

## Decisions recorded

- A batch (one deposit, one prefix) bounds the sidecar.
- Serialization: JSON header with inline or companion JSON Lines entries; YAML accepted for authoring; Parquet deferred.
- First supported specs: FHIR 4.0.1 with US Core (6.1.0 for Synthea test data), OMOP CDM 5.4, C-CDA 2.1.
- SHA-256 required, MD5 optional.
- `file_id` minted by the generator as a deterministic UUID; platform IDs attached as `external_ids`.
- Use terms, access tier, date policy and de-identification class are not sidecar fields.
- Own schema, mapped to Croissant and Frictionless rather than adopting either as the base, because neither models subjects, interactions or conformance groups.
- Register values (source IDs, buckets, delivery roles) are data issued per source as a descriptor file. The schema defines the descriptor's shape.
- PPRL linkage IDs never appear in a sidecar; consent and withdrawal batches identify persons by subject ID only. Matching to PPRL linkage IDs happens inside the RDDC through the participants table (plan Table 3, Table 17).
